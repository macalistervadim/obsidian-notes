### Архитектурный чек-лист: что было создано с нуля

В первой главе мы сознательно воздержались от преждевременного написания бизнес-логики торгового ядра, сосредоточившись на инженерной платформе. Такой подход исключил классический сценарий накопления технического долга и обеспечил проекту устойчивость к дальнейшим масштабным изменениям.

#### 1. Декларативное управление зависимостями и рантаймом
* **Отказ от устаревшего стека:** Вместо связки `pip + requirements.txt` и медленного `Poetry` проектом управляет высокопроизводительный инструмент **`uv`** на базе Rust.
* **Единый источник истины:** В файле `pyproject.toml` зафиксированы спецификации **PEP 621** (метаданные) и **PEP 735** (группа `dev`), а рантайм жестко ограничен версией `Python >= 3.13`.
* **Воспроизводимость:** Lock-файл `uv.lock` гарантирует детерминированность сборок на любых рабочих станциях и в CI-конвейерах.

#### 2. Масштабируемая структура кодовой базы (`src-layout`)
* Проект разбит на изолированные слои с направлением зависимостей от транспорта к хранилищу:
  * `api/` — маршрутизация запросов и обработка протоколов HTTP/WebSocket;
  * `schemas/` — контракты DTO на базе строгой типизации Pydantic;
  * `services/` — чистая бизнес-логика предметной области инвестиций;
  * `repositories/` — слой абстракции над базами данных и кэшем;
  * `core/` — инфраструктурное ядро, настройки и логирование.
* Использование компоновки `src-layout` полностью исключило ложноположительный импорт незаинсталлированного кода при тестировании.

#### 3. Наблюдаемость и многоуровневое логирование
* Библиотека **`structlog`** встроена в контекст жизненного цикла приложения (`lifespan`).
* Реализовано динамическое переключение форматов вывода: читаемый цветной вывод для консоли разработчика в режиме `dev` и структурированный сериализованный JSON для централизованных сборщиков в режиме `prod`.

#### 4. Промышленная контейнеризация и оркестрация
* Написан многослойный `Dockerfile` с двухэтапной сборкой `uv sync`, кэшированием слоев BuildKit, компиляцией байт-кода и запуском приложения от непривилегированного пользователя `appuser`.
* Манифест `docker-compose.yml` сегментирован с помощью механизма **`profiles`**, позволяя изолированно запускать боевой сервис (`prod`), контур разработки с горячей перезагрузкой (`dev`) и локальный SMTP-перехватчик Mailpit (`tools`).

#### 5. Строгий Quality Gate и автоматизация
* Линтер и форматтер **`ruff`** обеспечивает соблюдение PEP 8, оптимизацию коллекций под Python 3.13 и блокировку нежелательных вызовов `print()`.
* Анализатор **`mypy`** переведен в строгий режим (`strict = true`), исключая использование неявных типов `Any` и пропущенных сигнатур.
* Утилита **`tuna`** предоставляет защищенный HTTPS-туннель для сквозной отладки входящих брокерских вебхуков.
* Диспетчер команд **`just`** и файл `Justfile` свели весь комплекс рутинных операций к коротким командам `just run`, `just check` и `just dev-up`.

### Итоговая файловая карта проекта TradePulse

К моменту завершения первой главы структура репозитория имеет следующий законченный вид:

```text
tradepulse/
├── .env.example                # Шаблон переменных окружения
├── .gitignore                  # Исключения системы контроля версий Git
├── .dockerignore               # Исключения контекста сборки Docker
├── .python-version             # Фиксация рантайма Python 3.13
├── docker-compose.yml          # Манифест оркестрации с профилями (prod, dev, tools)
├── Dockerfile                  # Многоэтапный сценарий сборки production-образа
├── Justfile                    # Декларативный интерфейс запуска команд проекта
├── pyproject.toml              # Центральный манифест проекта (PEP 621 / PEP 735)
├── README.md                   # Документация и инструкции по развертыванию
├── uv.lock                     # Детерминированный срез графа зависимостей
├── src/
│   └── tradepulse/             # Основной исполняемый пакет приложения
│       ├── __init__.py
│       ├── main.py             # Точка входа ASGI и lifespan-управление
│       ├── api/                # Транспортный уровень (HTTP / WebSocket)
│       │   ├── __init__.py
│       │   └── v1/             # Версионированные контроллеры
│       │       └── __init__.py
│       ├── core/               # Инфраструктурное ядро
│       │   ├── __init__.py
│       │   ├── config.py       # Pydantic-настройки приложения
│       │   └── logger.py       # Конфигурация structlog (dev / test / prod)
│       ├── models/             # Доменные сущности и ORM-модели
│       ├── schemas/            # DTO-контракты валидации Pydantic
│       ├── services/           # Модули прикладной бизнес-логики
│       └── repositories/       # Слой работы с источниками данных
└── tests/                      # Набор тестовых сценариев
    ├── __init__.py
    └── conftest.py             # Глобальная конфигурация фикстур pytest
```

### Что ждет читателя во второй главе

Инженерный фундамент сервиса полностью подготовлен. Теперь проект готов к реализации предметной области финтех-платформы:
* Мы спроектируем архитектуру конфигурации через `pydantic-settings` с валидацией секретов;
* Подключим реляционную базу данных PostgreSQL через асинхронный драйвер `asyncpg` и современную ORM SQLAlchemy 2.0;
* Настроим механизм автоматических миграций схем с помощью Alembic;
* Создадим первые доменные модели для учета финансовых активов, котировок и торговых счетов пользователей платформы `TradePulse`.
