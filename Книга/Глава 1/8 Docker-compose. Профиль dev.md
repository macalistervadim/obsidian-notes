## 1.4. Разделение окружений: Docker Compose Profiles

### О чем эта подглава
В этой части мы настроим разделение конфигураций для локальной разработки и боевого запуска без дублирования файлов манифестов.

* **Что сделаем:** перейдем от разрозненных compose-файлов к единому декларативному манифесту `docker-compose.yml` на базе механизма профилей (`profiles`), добавим режим горячей перезагрузки (`hot-reload`) и подключим изолированный сервис отладки почты (Mailpit).
* **Исходное состояние проекта:** в корне репозитория присутствует настроенный `Dockerfile` для сборки сервиса `tradepulse` (по итогам подглавы 1.3).
* **Ветка в репозитории:** `chapter-01-compose-profiles` (готовый результат для тех, кто читает главу изолированно).

> **Что почитать для углубления:**
> * Официальная документация Docker Compose: раздел *«Using Compose profiles»*.
> * Э. Моуэт, *«Использование Docker»* (O'Reilly / ДМК Пресс) — для детального понимания механизмов изоляции сетей и томов.

### Проблема фрагментации окружений

В промышленной разработке сервис существует минимум в двух несовместимых режимах:
* **Development:** обязательна автоперезагрузка сервера при изменении файлов (`--reload`), монтирование исходного кода хоста внутрь контейнера, доступ к вспомогательным инструментам отладки (почтовые заглушки, мок-серверы).
* **Production:** неизменяемый легковесный образ, отсутствие проброса хостовых директорий, запуск без сторонних утилит и отладочных флагов.

Традиционный подход с файлами `docker-compose.dev.yml` и `docker-compose.prod.yml` приводит к дублированию настроек сетей (`networks`) и томов (`volumes`). Решение современного Docker Compose — директива `profiles`.

Принцип прост:
1. **Сервисы без профиля** запускаются всегда по умолчанию (`docker compose up`).
2. **Профилированные сервисы (`profiles: ["имя"]`)** игнорируются, пока профиль не активирован явно через флаг `--profile` или файл переменного окружения `.env`.

### Настройка единого манифеста

Обновите или создайте файл `docker-compose.yml` в корне проекта `tradepulse`:

```yaml
services:
  # ---------------------------------------------------------
  # 1. Боевой сервис API (профиль "prod")
  # ---------------------------------------------------------
  api:
    build:
      context: .
      dockerfile: Dockerfile
    image: tradepulse-api:latest
    container_name: tradepulse-api
    restart: unless-stopped
    ports:
      - "8000:8000"
    environment:
      - PYTHONUNBUFFERED=1
      - ENVIRONMENT=production
    networks:
      - tradepulse-network
    profiles:       
      - prod         

  # ---------------------------------------------------------
  # 2. Сервис для активной разработки (профиль "dev")
  # ---------------------------------------------------------
  api-dev:
    build:
      context: .
      dockerfile: Dockerfile
    image: tradepulse-api:dev
    container_name: tradepulse-api-dev
    command: >
      uvicorn tradepulse.main:app
      --app-dir src
      --host 0.0.0.0
      --port 8000
      --reload
    volumes:
      - ./src:/app/src:ro
    ports:
      - "8000:8000"
    environment:
      - PYTHONUNBUFFERED=1
      - ENVIRONMENT=development
      - DEBUG=True
    networks:
      - tradepulse-network
    profiles:
      - dev

  # ---------------------------------------------------------
  # 3. Вспомогательная утилита: локальный SMTP-сервер Mailpit
  # ---------------------------------------------------------
  mailpit:
    image: axllent/mailpit:latest
    container_name: tradepulse-mailpit
    ports:
      - "8025:8025"  # Веб-панель для просмотра писем
      - "1025:1025"  # SMTP-порт для отправки из приложения
    networks:
      - tradepulse-network
    profiles:
      - dev
      - tools

networks:
  tradepulse-network:
    driver: bridge
```

### Практические сценарии запуска

#### Сценарий 1. Запуск окружения разработки (⁠dev⁠)

Для работы над кодом приложения выполните команду:

```
docker compose --profile dev up
```

Compose запустит контейнеры ⁠api-dev⁠ и ⁠mailpit⁠. Обратите внимание: монтирование ⁠./src:/app/src:ro⁠ установлено в режиме Read-Only (⁠:ro⁠). Контейнер не сможет случайно перезаписать исходники на хосте, но Uvicorn мгновенно отреагирует на любые изменения в директории ⁠src/tradepulse/⁠.

Веб-интерфейс перехватчика писем Mailpit доступен в браузере по адресу:

⁠`http://localhost:8025`

##### Грабли: Конфликт портов при смене профилей

Если в терминале появляется ошибка:

> Bind for 0.0.0.0:8000 failed: port is already allocated⁠

это означает, что порт ⁠8000⁠ занят ранее запущенным контейнером другого профиля или локальным процессом.

1) Остановите активный Compose-проект:
   
   ```bash
   docker compose down
   ```
   
2) Если порт занят посторонним контейнером, найдите и остановите его:
   
   ```bash
	docker ps --filter "publish=8000"
	docker rm -f <ID_или_имя_контейнера>
   ```

3) Если порт держит локальный процесс на хосте (Linux/macOS):
   
   ```bash
	lsof -i :8000
	kill -9 <PID>
   ```
   ⁠
#### Сценарий 2. Запуск утилит без бэкенда (⁠tools⁠)

Если вам требуется только почтовый сервер для ручного тестирования или интеграционных тестов без запуска самого API:

```bash
docker compose --profile tools up mailpit -d
```

#### Сценарий 3. Автоматизация через ⁠.env⁠

Чтобы не передавать флаг ⁠--profile⁠ вручную при каждой сборке, зафиксируйте профиль в локальном конфигурационном файле ⁠.env⁠ в корне проекта:

```env
COMPOSE_PROFILE=dev
```

После этого вызов стандартных команд автоматически работает с профилем разработки:

```bash
# Запуск dev-окружения:
docker compose up -d

# Остановка контейнеров dev-окружения:
docker compose down

```

### Контрольная точка

К этому моменту в проекте ⁠tradepulse⁠ подготовлена декларативная конфигурация оркестрации:

1. Создан файл ⁠docker-compose.yml⁠ с профилями ⁠prod⁠, ⁠dev⁠ и ⁠tools⁠.

2. Настроен файл ⁠.env⁠ с переменной ⁠COMPOSE_PROFILES=dev⁠.

3. Локальный сервер API поднимается с активным hot-reload, а веб-интерфейс Mailpit доступен на порту 8025.
