### О чем эта подглава
В этой части мы настроим безопасный публичный туннель к локальному экземпляру `TradePulse`, чтобы принимать входящие сетевые события (вебхуки) от внешних биржевых шлюзов и платежных систем без развертывания сервиса на сервере.

* **Что сделаем:** разберем проблему «серого» IP-адреса и NAT при локальной отладке вебхуков, установим и сконфигурируем утилиту туннелирования `tuna`, получим временный публичный HTTPS-домен, протестируем сквозную доставку запросов из глобальной сети на локальный эндпоинт FastAPI и рассмотрим обработку сигналов безопасности.
* **Исходное состояние проекта:** в проекте настроена строгая типизация через `mypy` и линтинг `ruff`, запущен локальный сервер FastAPI с эндпоинтом `/health` на порту 8000 (по итогам подглавы 1.10).
* **Ветка в репозитории:** `chapter-01-tuna-tunnel` (готовый результат для тех, кто читает главу изолированно).

> **Что почитать для углубления:**
> * Спецификация Webhooks: архитектурные шаблоны обработки асинхронных уведомлений (*Push-notifications over HTTP*).
> * Билл Любанович, *«FastAPI»* (O'Reilly, 2023) — обработка фоновых задач и получение внешних POST-запросов.
> * Тим Питерс, *«Программирование бэкенда на Python. Практическое руководство»* (БХВ, 2025) — раздел о безопасности входящих вебхуков, проверке подписей HMAC и идемпотентности.

### Архитектурная проблема: почему localhost невидим для внешнего мира

При разработке финтех-сервисов взаимодействие между системами редко ограничивается классической схемой «клиент запросил $\rightarrow$ сервер ответил». Биржи, брокерские шлюзы и процессинговые центры общаются асинхронно с помощью механизма **Webhooks**:
1. Наша система отправляет заявку на открытие торговой позиции.
2. Биржевой шлюз ставит операцию в очередь матчинга.
3. Как только заявка исполняется, сервер биржи инициирует встречный HTTP POST-запрос на специальный адрес нашего сервиса (`/api/v1/webhooks/orders`).

Когда вы запускаете FastAPI на локальном компьютере (`http://127.0.0.1:8000`), машина находится за сетевым экраном провайдера (NAT) или роутером с динамическим приватным IP-адресом. Внешний сервер биржи физически не может отправить пакет на `localhost` или `192.168.x.x` разработчика.

Классические обходные пути (ручная настройка проброса портов в роутере — Port Forwarding, аренда внешнего VDS для каждого коммита) отнимают рабочее время и создают дыры в периметре безопасности домашней или офисной сети.

Инструмент **`tuna`** решает эту проблему за счет концепции обратного туннелирования (*reverse tunneling*).

### Как работает туннелирование трафика

Механизм обратного прокси строит защищенную сетевую магистраль в три этапа:

```text
┌───────────────────────┐             ┌─────────────────────┐             ┌─────────────────────────┐
│ Внешняя биржа / шлюз  │ ──HTTPS──>  │    Сервер Tuna      │ ──Защищенный│  Локальная машина       │
│ (POST https://*.tuna) │             │  (публичный узел)   │   туннель   │  (клиент tuna:8000)     │
└───────────────────────┘             └─────────────────────┘   (TCP/WS)  └────────────┬────────────┘
                                                                                       │ localhost
                                                                                       ▼
                                                                          ┌─────────────────────────┐
                                                                          │  TradePulse (FastAPI)   │
                                                                          └─────────────────────────┘
```

1. Локальный консольный агент `tuna` устанавливает исходящее постоянное соединение (TCP или secure WebSocket) с публичным сервером-реле. Так как соединение *исходящее*, домашний маршрутизатор и файрвол не блокируют его.
2. Публичный сервер выделяет вашему сеансу уникальный поддомен с готовым валидным SSL-сертификатом (например, `https://tradepulse-dev.tuna.am`).
3. Любой внешний запрос, поступающий на этот URL из интернета, моментально ретранслируется через открытый туннель прямо в ваш локальный порт `8000`.

### Шаг 1. Установка и запуск туннеля

Утилита `tuna` распространяется в виде единого скомпилированного бинарного файла, не требующего дополнительных системных зависимостей.

#### Установка агента
Для Linux / macOS установка выполняется через готовый скрипт либо менеджер пакетов:

```bash
# Установка через curl (или brew install tuna)
curl -sSL https://get.tuna.am | sh
```

Проверьте успешную установку вызовом справки:

```bash
tuna --help
```

Для запуска туннеля необходимо зарегистрировать аккаунт и получить токен в Tuna:

```shell
tuna login
```

Терминал выдаст вам ссылку вида `Open in your browser: https://my.tuna.am/client_login?redirect_url=http://127.0.0.1:53420/client_login&secret=123 `

Откройте в своем браузере данную ссылку и пройдите регистрацию, после чего вам будет предложено перейти обратно в терминал с уже вставленным токеном:

```shell
INFO[16:42:44] Login as m@gmail.com        
INFO[16:42:44] Token saved    
```

#### Запуск туннеля для TradePulse
Убедитесь, что ваше приложение FastAPI запущено в соседнем терминале:

```bash
uv run uvicorn tradepulse.main:app --app-dir src --reload --port 8000
```

Во втором окне терминала поднимите туннель, указав целевой локальный порт:

```bash
tuna http 8000
```

Консольный интерфейс `tuna` отобразит статус подключения и сгенерированный публичный адрес:

```text
Tuna Tunnel Online

Status       : Connected
Forwarding   : https://a1b2c3d4.tuna.am -> http://localhost:8000
Web Inspect  : [http://127.0.0.1:4040](http://127.0.0.1:4040)
Metrics      : 0 req/sec
```

### Шаг 2. Практическая проверка доставки внешнего запроса

Теперь эндпоинт проверки жизнеспособности сервиса доступен не только внутри локальной сети, но и из любой точки глобального интернета.

Проверьте доступность через утилиту `curl` (или отправьте ссылку коллеге / откройте со смартфона без подключения к домашнему Wi-Fi):

```bash
curl -i https://a1b2c3d4.tuna.am/health
```

Ответ сервера:
```http
HTTP/2 200 
content-type: application/json
date: Mon, 26 Oct 2026 10:30:00 GMT
server: uvicorn

{"status":"ok"}
```

В логах `uvicorn` и `structlog` зафиксируется входящий запрос, а веб-дашборд `tuna` на порту `4040` покажет детальную структуру сетевых заголовков и тело запроса.

### Инженерные нюансы и безопасность при работе с туннелями

1. **Безопасность заголовка `Host` и доверенные прокси (`Trusted Hosts`):**  
   Когда запрос проходит через обратный прокси, реальный клиентский IP-адрес помещается в заголовок `X-Forwarded-For`, а вызываемый домен — в `X-Forwarded-Host`. При включении в FastAPI встроенного middleware `TrustedHostMiddleware` обязательно добавьте маску доменов туннеля в список доверенных хостов, иначе сервер вернет ошибку `400 Bad Request`.
2. **Исключение туннелей из боевых сред:**  
   Утилиты вроде `tuna` или `ngrok` категорически запрещено запускать на продакшен-серверах. Это исключительно инструмент локального контура разработчика для отладки вебхуков и интеграционных проверок.
3. **Валидация подписей входящих хуков:**  
   Поскольку сгенерированный публичный адрес потенциально доступен любому пользователю в сети, реальные обработчики вебхуков всегда должны валидировать криптографическую подпись отправителя (HMAC SHA-256) в заголовках запроса.

> **Грабли: Сессионные обрывы при неактивности**  
> Если туннель находится в режиме ожидания длительное время без входящего трафика, некоторые провайдеры могут разрывать неактивные TCP-сессии. Для предотвращения разрыва используйте периодический keep-alive пинг либо перезапускайте туннель перед началом сеанса тестирования вебхуков.
