## 1.6. Настройка структурированного логирования для различных окружений: dev, test, prod

### О чем эта подглава
В этой части мы настроим гибкую систему логирования на базе библиотеки `structlog`, адаптированную под требования разработки, тестирования и боевой эксплуатации.

* **Что сделаем:** откажемся от стандартного `print()` и сырого вывода `logging`, настроим переключение форматов вывода (цветной человекочитаемый вывод для локальной консоли и сериализованный JSON для сборщиков логов), интегрируем логгер в жизненный цикл (`lifespan`) приложения FastAPI.
* **Исходное состояние проекта:** в проекте инициализирована структура пакетов с использованием `src-layout`, установлены базовые зависимости FastAPI в `pyproject.toml` (по итогам подглавы 1.5).
* **Ветка в репозитории:** `chapter-01-logging-setup` (готовый результат для тех, кто читает главу изолированно).

> **Что почитать для углубления:**
> * Официальная документация `structlog`: разделы *«Getting Started»* и *«Standard Library Integration»*.
> * Тим Питерс, *«Программирование бэкенда на Python. Практическое руководство»* (БХВ, 2025) — глава о наблюдаемости (Observability), трассировке и аудите событий.

> * Методология *«The Twelve-Factor App»*: фактор XI (Logs) — трактовка логов как потоков событий.

### Почему print() недопустим в продакшене

В учебных скриптах вывод информации традиционно выполняется функцией `print()`. Однако в промышленном веб-сервисе такой подход приводит к критическим проблемам:
* **Отсутствие метаданных:** `print()` не фиксирует временную метку события, имя вызывающего модуля и контекст выполнения.
* **Невозможность фильтрации:** нельзя динамически отключить отладочный спам на боевом сервере без ручного удаления строк из кода.
* **Несовместимость со сборщиками логов:** современные системы централизованного сбора логов (Elasticsearch, Loki, OpenSearch, Vector) требуют строго структурированных данных (JSON) с фиксированными ключами.

В профессиональной разработке поток событий разделяется по стандартным уровням важности:
* `DEBUG` — технические подробности для локальной отладки;
* `INFO` — штатные бизнес-события и сигналы готовности (старт воркера, успешное подключение);
* `WARNING` — нештатные ситуации, не прерывающие работу приложения;
* `ERROR` — исключения и сбои в обработке конкретного запроса;
* `CRITICAL` — фатальные аварии (недоступность СУБД, падение фонового процесса).

Формат лога должен строго соответствовать целевому окружению:
1. **`dev` (локальная разработка):** человекочитаемый, цветной вывод с подробным уровнем `DEBUG` в консоли терминала.
2. **`test` (прогон тестов):** уровень `WARNING` и компактный формат, не засоряющий консольный вывод тестового фреймворка `pytest`.
3. **`prod` (боевое окружение):** строгий JSON с уровнем `INFO` и выше, потоком отправляемый в `stdout` контейнера.

Для реализации этой схемы мы используем библиотеку **`structlog`** вместе с **`rich`** для рендеринга терминальной графики.

### Шаг 1. Установка зависимостей

Добавьте библиотеки в список зависимостей проекта через пакетный менеджер `uv`:

```bash
uv add structlog rich
```

Пакетный менеджер автоматически добавит зависимости в манифест `pyproject.toml` и пересчитает хэши в `uv.lock`.

### Шаг 2. Создание модуля конфигурации логирования

Создайте файл для модуля логирования в директории ядра сервиса:

```bash
touch src/tradepulse/core/logger.py
```

Откройте `src/tradepulse/core/logger.py` и реализуйте фабрику конфигурации:

```python
import logging
import sys
from typing import Literal

import structlog

# Допустимые типы сред развертывания
EnvironmentType = Literal["dev", "test", "prod"]


def setup_logging(env: EnvironmentType = "dev") -> None:
    """Конфигурирует форматирование и уровень детализации логирования под конкретное окружение."""

    # 1. Сегментация уровня важности и процессоров форматирования
    if env == "dev":
        log_level = logging.DEBUG
        # Цветной консольный вывод для локальной отладки разработчиком
        renderer = structlog.dev.ConsoleRenderer(colors=True)
    elif env == "test":
        log_level = logging.WARNING
        # Минималистичный текстовый формат key=value для подавления шума в тестах
        renderer = structlog.processors.KeyValueRenderer()
    else:  # prod
        log_level = logging.INFO
        # Машиночитаемый JSON для серверных сборщиков логов
        renderer = structlog.processors.JSONRenderer()

    # 2. Инициализация конвейера обработки structlog
    structlog.configure(
        processors=[
            # Фиксация уровня записи (debug, info, warning, error)
            structlog.stdlib.add_log_level,
            # Добавление временного штампа события в стандарте ISO-8601
            structlog.processors.TimeStamper(fmt="iso"),
            # Формирование итоговой структуры записи
            renderer,
        ],
        logger_factory=structlog.PrintLoggerFactory(file=sys.stdout),
    )

    # 3. Базовая настройка стандартной библиотеки logging
    logging.basicConfig(level=log_level)


# Экземпляр логгера для импорта в модули бизнес-логики и роутеры
logger = structlog.get_logger()
```

### Шаг 3. Интеграция с жизненным циклом FastAPI

Для инициализации настроек логирования при старте ASGI-сервера воспользуемся современным механизмом управления жизненным циклом FastAPI — контекст-менеджером `lifespan`.

Откройте файл `src/tradepulse/main.py` и свяжите логгер с событиями запуска и остановки приложения:

```python
from contextlib import asynccontextmanager
from typing import AsyncIterator

from fastapi import FastAPI
from tradepulse.core.logger import logger, setup_logging


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    # События при запуске (startup)
    setup_logging(env="dev")
    logger.info("Сервис TradePulse успешно запущен", version="0.1.0")
    yield
    # События при завершении работы (shutdown)
    logger.info("Сервис TradePulse остановлен")


app = FastAPI(
    title="TradePulse API",
    lifespan=lifespan,
)


@app.get("/health")
async def healthcheck() -> dict[str, str]:
    logger.debug("Вызов проверки жизнеспособности сервиса", endpoint="/health")
    return {"status": "ok"}
```

### Шаг 4. Практическая проверка и запуск

Запустите сервер разработки с передачей корневой директории исходных кодов:

```bash
uv run uvicorn tradepulse.main:app --app-dir src --reload
```

> **Грабли: Специфика импортов при использовании src-layout**  
> При архитектуре с изолированной директорией `src/` интерпретатор Python, вызванный из корня, по умолчанию не находит модуль `tradepulse` внутри переменной `sys.path`.
> 
> Для решения этой проблемы используйте один из двух подходов:
> 1. Всегда явно передавайте флаг `--app-dir src` серверу Uvicorn при локальном запуске:
>    ```bash
>    uv run uvicorn tradepulse.main:app --app-dir src --reload
>    ```
> 2. Либо установите проект в виртуальное окружение в режиме редактирования (editable install):
>    ```bash
>    uv pip install -e .
>    ```

Отправьте проверочный запрос на эндпоинт `/health` через curl или откройте адрес в браузере:

```bash
curl [http://127.0.0.1:8000/health](http://127.0.0.1:8000/health)
```

В терминале разработки отобразится структурированная и подсвеченная цветом запись:

```text
2026-10-15T08:10:00.123456Z [info     ] Сервис TradePulse успешно запущен version=0.1.0
2026-10-15T08:10:05.654321Z [debug    ] Вызов проверки жизнеспособности сервиса endpoint=/health
```

При переключении режима на `setup_logging(env="prod")` (или при чтении переменной окружения `ENVIRONMENT=production`) вывод автоматически перестраивается в плоский JSON, готовый для индексации в хранилище логов:

```json
{"event": "Сервис TradePulse успешно запущен", "level": "info", "timestamp": "2026-10-15T08:10:00.123456Z", "version": "0.1.0"}
{"event": "Вызов проверки жизнеспособности сервиса", "level": "debug", "timestamp": "2026-10-15T08:10:05.654321Z", "endpoint": "/health"}
```

### Контрольная точка
К этому моменту подсистема наблюдаемости сервиса подготовлена:
1. Зависимости `structlog` и `rich` зафиксированы в `uv.lock`.
2. В модуле `src/tradepulse/core/logger.py` настроены обработчики и форматирование под среды `dev`, `test` и `prod`.
3. Точка входа `main.py` регистрирует логгер в жизненном цикле приложения, а контрольный эндпоинт `/health` подтверждает запись структурированных атрибутов.
