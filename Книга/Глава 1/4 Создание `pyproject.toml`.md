### От хаоса requirements.txt к единому источнику истины

Исторически конфигурация проектов на Python была фрагментирована: метаданные пакета описывались в `setup.py` или `setup.cfg`, списки зависимостей разносились по отдельным текстовым файлам (`requirements.txt`, `requirements-dev.txt`), а инструменты анализа кода требовали собственные конфигурационные файлы (`.flake8`, `mypy.ini`, `pytest.ini`). Это приводило к захламлению корня репозитория и отсутствию единого источника истины.

Современным стандартом декларативного описания проектов на Python является спецификация **PEP 621**, закрепившая файл **`pyproject.toml`** в качестве центрального манифеста. Инструмент `uv` полностью опирается на этот стандарт, исключая необходимость использования устаревших форматов.

В результате выполнения команд инициализации и добавления зависимостей на предыдущем шаге в корне проекта `TradePulse` сгенерирован следующий манифест:

```toml
[project]
name = "tradepulse"
version = "0.1.0"
description = "Высоконагруженный сервис для работы с ценными бумагами"
readme = "README.md"
requires-python = ">=3.13"
dependencies = [
    "fastapi>=0.115.0",
    "pydantic>=2.9.0",
    "uvicorn[standard]>=0.31.0",
]

[dependency-groups]
dev = [
    "pytest>=8.3.0",
    "mypy>=1.11.0",
    "ruff>=0.6.0",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

### Разбор ключевых секций манифеста

#### 1. Секция `[project]` (метаданные по PEP 621)
Содержит паспортные данные сервиса: системное имя, версию и описание.
* Параметр `requires-python = ">=3.13"` жестко ограничивает минимальную версию рантайма на уровне экосистемы. При попытке установить зависимости на устаревшем интерпретаторе `uv` прервет операцию с понятной ошибкой.

#### 2. Массив `dependencies` (основные зависимости)
Здесь фиксируются библиотеки, необходимые для непосредственной работы приложения в боевой среде (FastAPI, валидатор Pydantic, ASGI-сервер Uvicorn).
* Обратите внимание на оператор `>=`: в манифесте задаются гибкие границы совместимости, тогда как **абсолютно точные версии, ссылки на wheel-архивы и контрольные хэши** фиксируются в автоматически созданном файле `uv.lock`.

#### 3. Группы окружений `[dependency-groups]` (стандарт PEP 735)
Вместо устаревших файлов вроде `requirements-dev.txt` зависимости разделяются по группам прямо в TOML-файле.
* Инструменты тестирования (`pytest`), статической типизации (`mypy`) и линтинга (`ruff`) вынесены в группу `dev`.
* При сборке компактного Docker-образа для продакшена флаг `--no-dev` исключает эту группу из итогового контейнера.

#### 4. Секция `[build-system]` (бэкенд сборки по PEP 517/518)
Определяет утилиту, отвечающую за сборку исходного кода в распространяемый архив (`.whl` или `.tar.gz`).
* По умолчанию `uv` использует легковесный и быстрый бэкенд **`hatchling`**, позволяющий упаковать `TradePulse` в стандартный `.whl`-архив без бойлерплейта и нативно поддерживающий компоновку каталогов `src-layout`.

### Синхронизация и детерминированность

Благодаря тому, что `uv` автоматически синхронизирует манифест с файлом блокировок, разработчику не требуется править точные версии вручную. 

Команда синхронизации гарантирует строгое соответствие среды манифесту:

```bash
uv sync
```

Инструмент за доли секунды сверяет манифест `pyproject.toml`, lock-файл `uv.lock` и фактически установленные пакеты в локальном каталоге `.venv`.

> **Грабли: Ручная правка lock-файла**  
> Никогда не вносите правки в `uv.lock` вручную. Для добавления или обновления библиотек всегда используйте CLI:
> ```bash
> # Для продакшен-зависимостей:
> uv add <название_пакета>
>
> # Для утилит разработки:
> uv add --dev <название_пакета>
> ```
> Это гарантирует автоматический пересчет хэшей безопасности и проверку разрешения графа зависимостей.
