### Архитектурные риски хаотичной структуры

Распространенная ошибка при старте проектов на FastAPI — складывать все обработчики, схемы и запросы к базе в единый файл `main.py` или бессистемно разбрасывать модули по корню репозитория. В демонстрационных примерах это экономит время, но в промышленном сервисе уровня `TradePulse` неминуемо влечет технический долг:
* **Циклические импорты (circular imports):** взаимная зависимость моделей, роутеров и сервисов блокирует запуск Python-интерпретатора.
* **Размытие зон ответственности:** смешивание бизнес-расчетов, валидации протокола HTTP и прямых SQL-запросов в одном теле функции делает невозможным модульное тестирование (Unit Testing).
* **Сложность онбординга:** новым разработчикам трудно ориентироваться в кодовой базе без четких границ между слоями.

Для `TradePulse` мы используем модульную слоистую архитектуру с компоновкой **`src-layout`**.

### Почему промышленный стандарт — это src-layout

В экосистеме Python долгое время применялась схема `flat-layout` (когда пакет приложения лежит непосредственно в корне репозитория). В enterprise-разработке стандартом де-факто стал `src-layout` по следующим причинам:

1. **Защита от ложноположительных тестов:** При запуске `pytest` из корня репозитория Python автоматически добавляет текущую рабочую директорию в `sys.path`. При `flat-layout` тесты могут обращаться к незаинсталлированным локальным файлам в обход виртуального окружения. Наличие папки `src/` форсирует выполнение тестов строго против пакета, установленного через `uv sync` или `uv pip install -e .`.
2. **Изоляция инфраструктурной обвязки:** Конфигурации CI/CD, манифесты Docker, файлы линтеров и документация отделены от исполняемого Python-пакета.
3. **Детерминированная сборка дистрибутива:** Инструменты сборки (включая `hatchling`) упаковывают в wheel-архив исключительно содержимое `src/`, предотвращая случайное попадание тестов и локальных скриптов в продакшен-сборку.

### Шаг 1. Формирование дерева каталогов TradePulse

Выполните команды в терминале из корня проекта для создания каркаса приложения:

```bash
mkdir -p src/tradepulse/{api/v1,core,models,schemas,services,repositories} tests
touch src/tradepulse/{__init__.py,main.py}
touch src/tradepulse/api/__init__.py src/tradepulse/api/v1/__init__.py
touch src/tradepulse/core/{__init__.py,config.py}
touch tests/{__init__.py,conftest.py}
```

В результате формируется прозрачная структура каталогов:

```text
tradepulse/
├── .venv/                      # Изолированное виртуальное окружение
├── src/
│   └── tradepulse/             # Основной исполняемый пакет
│       ├── __init__.py
│       ├── main.py             # Точка входа в приложение (ASGI entry point)
│       ├── api/                # Транспортный уровень (HTTP / WebSocket)
│       │   ├── __init__.py
│       │   └── v1/             # Версионирование эндпоинтов
│       │       └── __init__.py
│       ├── core/               # Инфраструктурное ядро и синглтоны
│       │   ├── __init__.py
│       │   └── config.py       # Pydantic-настройки и чтение .env
│       ├── models/             # ORM-модели базы данных (SQLAlchemy / Tortoise)
│       ├── schemas/            # DTO-контракты Pydantic (запросы и ответы)
│       ├── services/           # Чистая бизнес-логика предметной области
│       └── repositories/       # Слой прямого доступа к хранилищам (PostgreSQL / Redis)
├── tests/                      # Автотесты (модульные и интеграционные)
│   ├── __init__.py
│   └── conftest.py             # Глобальные фикстуры pytest
├── pyproject.toml              # Декларативный манифест проекта и зависимости
├── uv.lock                     # Детерминированный lock-файл зависимостей
└── README.md                   # Документация проекта
```

### Шаг 2. Разделение зон ответственности слоев

Каждый каталог внутри `src/tradepulse/` имеет строго очерченные границы и правила взаимодействия:

| Слой / Директория | Назначение | Допустимые зависимости | Чего содержать не должен |
| :--- | :--- | :--- | :--- |
| **`core/`** (Ядро) | Глобальные настройки (`settings`), конфигурация логов, пулы коннектов. | Внешние библиотеки, утилиты. | Знание о маршрутах HTTP или бизнес-логике. |
| **`schemas/`** (Контракты) | Pydantic DTO: валидация payload'ов, структуры ответов. | Стандартные типы, `pydantic`. | Логику работы с БД, вызовы внешних API. |
| **`api/`** (Транспорт) | Прием HTTP-запросов, маршрутизация, вызов сервисов, возврат статус-кодов. | `schemas/`, `services/`, `core/`. | Прямые SQL-запросы, математические расчеты. |
| **`services/`** (Бизнес-логика) | Алгоритмы торговли, расчет рисков, обработка транзакций. | `repositories/`, `models/`, `schemas/`. | Привязку к FastAPI (`Request`, HTTP-статусы). |
| **`repositories/`** (Данные) | Инкапсуляция обращений к PostgreSQL/Redis, выполнение запросов. | `models/`, драйверы СУБД. | Обработку бизнес-правил, парсинг запросов клиента. |

> **Архитектурное правило:** Зависимости всегда направлены сверху вниз:  
> `api` $\rightarrow$ `services` $\rightarrow$ `repositories`.  
> Слой `services` не знает, откуда к нему обратились — через FastAPI HTTP-роутер, фоновую задачу Celery или команду консоли CLI. Это обеспечивает полную независимость бизнес-логики от фреймворка.
