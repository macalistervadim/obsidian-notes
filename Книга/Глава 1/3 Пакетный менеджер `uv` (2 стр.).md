### Ограничения pip и проблемы повторяемости сборок

Исторически в стандартную поставку Python входит утилита `pip` (*Package Installer for Python*). Долгое время связка из `pip`, стандартного модуля `venv` и файла `requirements.txt` являлась базовым стандартом индустрии. Однако по мере перехода к микросервисной архитектуре и сложным графам зависимостей этот подход выявил критические архитектурные недостатки:

1. **Отсутствие детерминированности:** Классический `requirements.txt` не фиксирует полное дерево неявных (транзитивных) подзависимостей. Если в манифесте зафиксирована библиотека верхнего уровня без жесткого закрепления всех ее связей, сборка, стабильно работающая на рабочей машине сегодня, может сломаться завтра в CI/CD-пайплайне из-за несовместимого релиза стороннего вложенного пакета.
2. **Медленное разрешение зависимостей (*dependency resolution*):** Попытки решить эту проблему надстройками вроде `Poetry`, `Pipenv` или `PDM` привели к другой крайности: долгому вычислению графа версий, тяжеловесным сборкам и затянутому холодному старту контейнеров.
3. **Локальная компиляция:** Без предсобранных архивов разработчикам регулярно приходится компилировать C-расширения библиотек прямо во время установки.

> **Что такое формат Wheel (.whl)?**  
> В экосистеме Python библиотеки распространяются либо в виде архива исходных кодов (*sdist*), либо в виде предсобранных бинарных пакетов — **Wheel** (файлы с расширением `.whl`). Формат Wheel избавляет от долгой локальной компиляции C-расширений при установке: пакетный менеджер просто распаковывает уже готовый архив под целевую платформу за доли секунды.

Менеджер **`uv`**, разработанный компанией Astral (создателями линтера `ruff`), кардинально изменил рабочий процесс в экосистеме Python. Написанный на языке Rust, `uv` выступает как сверхбыстрая замена `pip`, `pip-tools`, `virtualenv` и менеджеров версий Python (`pyenv`), объединяя весь цикл управления проектом в рамках единого бинарного файла без внешних зависимостей.

### Архитектурные преимущества uv

* **Экстремальная производительность и кэширование:**  
  Благодаря алгоритму разрешения зависимостей PubGrub на Rust и многопоточной загрузке, `uv` разрешает зависимости и скачивает пакеты в 10–100 раз быстрее аналогов. Глобальный кэш на уровне ОС исключает повторное скачивание одних и тех же библиотек для разных проектов на одном компьютере.
* **Детерминированный lock-файл (`uv.lock`):**  
  Инструмент генерирует кроссплатформенный lock-файл, фиксирующий точные хэши безопасности, срезы версий и полное дерево связей пакетов. Это гарантирует 100% воспроизводимость сборки на машинах всей команды и на сервере.
* **Бесшовное управление версиями рантайма Python:**  
  `uv` самостоятельно скачивает, изолирует и настраивает требуемую версию CPython без ручной сборки интерпретатора из исходников или установки системных утилит вроде `pyenv`.
* **Следование стандартам PEP 517 / PEP 621 / PEP 735:**  
  Инструмент использует стандартные спецификации Python Packaging, концентрируя метаданные, зависимости и настройки сборщика в едином файле `pyproject.toml`.

### Практическая работа: инициализация TradePulse

#### 1. Создание каркаса и фиксация рантайма
Выполните команды в терминале для создания директории приложения, фиксации целевой версии интерпретатора и развертывания виртуального окружения:

```bash
# Инициализация каркаса приложения с генерацией pyproject.toml
uv init tradepulse --app

cd tradepulse

# Фиксация версии интерпретатора для проекта
uv python pin 3.13

# Создание изолированного виртуального окружения
uv venv
```

#### 2. Добавление и разделение зависимостей
Добавление пакетов выполняется атомарными командами без необходимости вручную править текстовые файлы:

```bash
# Установка базового веб-стека в основную группу зависимостей проекта
uv add fastapi "uvicorn[standard]" pydantic

# Добавление инструментов тестирования и статического анализа в dev-группу
uv add --dev ruff mypy pytest
```

В результате выполнения этих команд `uv` автоматически создаст и наполнит манифест `pyproject.toml`, а также сгенерирует файл блокировок `uv.lock`.

#### 3. Воспроизводимая сборка для боевой среды
Для синхронизации окружения на продакшен-сервере или внутри базового Docker-образа используется команда:

```bash
uv sync --frozen --no-dev
```

* Флаг `--frozen` запрещает обновление зависимостей и пересчет графа (гарантирует сборку строго по существующему `uv.lock`).
* Флаг `--no-dev` отсекает инструменты разработки (`ruff`, `mypy`, `pytest`), обеспечивая минимальный размер дистрибутива.

> **Грабли: Запуск команд вне окружения uv**  
> Если после создания виртуального окружения вы попытаетесь вызвать команду `uvicorn` или `pytest` напрямую из терминала хоста, вы рискуете получить ошибку `command not found` (если окружение не активировано через `source .venv/bin/activate`).
> 
> Рекомендуемый промышленный подход — выполнять команды через префикс `uv run`:
> ```bash
> uv run uvicorn --version
> ```
> В этом случае `uv` гарантированно исполняет бинарник внутри целевого `.venv` даже без ручной активации сессии.
