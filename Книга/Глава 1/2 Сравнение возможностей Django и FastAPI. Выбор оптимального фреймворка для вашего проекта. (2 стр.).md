### Проблема архитектурного выбора

Выбор базового веб-фреймворка — одно из тех ключевых решений, цена ошибки в которых проявляется не на этапе создания прототипа, а спустя полгода в продакшене. Неверно подобранный инструмент приводит либо к постоянной борьбе с жесткими рамками платформы, либо к написанию сотен строк инфраструктурного шаблонного кода (*boilerplate*), который можно было получить «из коробки».

Среди Python-разработчиков основное противостояние при проектировании серверных систем сегодня разворачивается между двумя зрелыми концепциями: классическим монолитным решением в лице **Django** (в связке с Django REST Framework) и минималистичным асинхронным API-инструментом в лице **FastAPI**.

### Django: концепция «Батарейки в комплекте»

Django создавался в эпоху, когда веб-приложение воспринималось как единый монолит, отвечающий одновременно за хранение данных, бизнес-логику, сессии пользователей и рендеринг HTML-страниц. Его ключевая философия — *batteries included* («всё включено»).

#### Сильные стороны
* **Готовая экосистема:** Из коробки доступны надежная реляционная ORM, встроенная система генерации миграций, аутентификация, валидация форм и проверенные механизмы защиты от CSRF, XSS и SQL-инъекций.
* **Административная панель:** Интерфейс для контент-менеджеров и операторов базы данных генерируется автоматически на основе объявленных моделей за считанные минуты.
* **Стандартизация:** Архитектурный паттерн MTV (Model-Template-View) жестко регламентирован. Любой разработчик, подключившись к новому Django-проекту, мгновенно ориентируется в структуре приложений, настроек и маршрутов.

#### Ограничения и компромиссы
* **Архитектурная тяжеловесность:** Инициализация полноценного приложения Django с разветвленным деревом `INSTALLED_APPS`, тяжелым контекстом конфигурации и шиной сигналов создает заметный оверхед по оперативной памяти. Для легковесных утилит или проксирующих микросервисов такой стек избыточен.
* **Сложность кастомизации ядра:** Гибкость Django раскрывается только до тех пор, пока вы не пытаетесь заменить штатные компоненты. Внедрение сторонней асинхронной ORM (например, SQLAlchemy 2.0) или переход на валидацию через Pydantic вместо сериализаторов DRF требует преодоления сопротивления внутренней архитектуры фреймворка.
* **Историческая синхронность:** Несмотря на активное развитие ASGI-режима и поддержку асинхронных представлений в последних версиях, большая часть сторонней экосистемы и глубокие уровни штатной ORM остаются синхронными.

### FastAPI: асинхронный микрофреймворк для API

FastAPI изначально проектировался под реалии микросервисной архитектуры, одностраничных приложений (SPA) и мобильных клиентов, где сервер выступает исключительно в роли высокопроизводительного интерфейса обмена структурированными данными (JSON).

#### Сильные стороны
* **Нативная асинхронность (ASGI):** Построенный поверх Starlette и AnyIO, фреймворк спроектирован для эффективной обработки тысяч конкурентных I/O-bound соединений (обращения к сторонним микросервисам, кэшу Redis, брокерам сообщений) без блокировки основного потока.
* **Строгая типизация через Pydantic:** Разработчик использует стандартные аннотации типов Python (`type hints`). На их основе фреймворк автоматически валидирует входящие тела запросов, сериализует исходящие ответы и возвращает информативные ошибки валидации с точностью до конкретного поля.
* **Автодокументация:** Из схемы типов и маршрутов «на лету» формируется интерактивная документация в стандартах Swagger UI и ReDoc. Это снимает проблему рассинхронизации документации и реального контракта API.
* **Система внедрения зависимостей (Dependency Injection):** Механизм `Depends` позволяет лаконично организовывать проверку прав доступа, сессии баз данных и логирование без использования тяжелых декораторов или глобального контекста.

#### Ограничения и компромиссы
* **Концепция «Сделай сам»:** FastAPI — это микрофреймворк. В нем нет встроенной базы данных, механизма миграций, админки или готовой системы пользователей. Архитектуру проекта, стек работы с БД (Alembic + SQLAlchemy / Tortoise-ORM) и механизм аутентификации разработчик обязан проектировать самостоятельно.
* **Человеческий фактор в архитектуре:** Из-за отсутствия жестких рамок неопытные команды часто превращают проект на FastAPI в хаотичный набор файлов, смешивая бизнес-логику с транспортным слоем в эндпоинтах.

### Сравнительный анализ характеристик

| Критерий | Django (+ DRF) | FastAPI |
| :--- | :--- | :--- |
| **Базовая парадигма** | Полнофункциональный монолитный комбайн | Специализированный микрофреймворк для API |
| **Работа с базой данных** | Мощная встроенная синхронная ORM | Свободный выбор (SQLAlchemy, Tortoise, SQLModel) |
| **Административный интерфейс** | Встроен по умолчанию | Отсутствует (требуются сторонние решения вроде SQLAdmin) |
| **Валидация данных** | Django Forms / DRF Serializers | Pydantic v2 (на базе Type Hints) |
| **Асинхронность** | Гибридная (ASGI над синхронным ядром) | Нативная от сетевого сокета до бизнес-логики |
| **Интерактивная документация** | Требует сторонних пакетов (drf-spectacular) | Генерируется автоматически из коробки |

### Практическая матрица принятия решений

Чтобы определить оптимальный инструмент, ответьте на три контрольных вопроса о характере проекта:

1. **Нужен ли интерфейс администрирования «вчера»?**  
   Если бизнесу с первой недели требуются визуальные инструменты для ручной модерации данных, редактирования каталогов или управления доступами — выбор в пользу **Django** сэкономит десятки часов разработки.
2. **Каков характер нагрузки?**  
   Для сервисов, проводящих 90% времени в ожидании сетевого ввода-вывода (*I/O-bound*) — стриминг биржевых котировок, опрос внешних REST/WebSocket API, кэширование в Redis или обработка вебхуков — **FastAPI** обеспечивает существенно более высокую пропускную способность на том же объеме серверных ресурсов.
3. **Монолит или микросервис?**  
   Для классических монолитных систем с серверным рендерингом страниц, интернет-магазинов или контентных платформ с развитыми связями между сущностями отлично подходит связка Django + PostgreSQL. Если создается изолированный независимый микросервис в контейнере Docker со своим хранилищем — минималистичность FastAPI будет оптимальной.

> **Почему для TradePulse мы выбираем FastAPI:**  
> Платформа `TradePulse` по своей природе ориентирована на интенсивный асинхронный I/O (обработка потоков котировок, интеграция с внешними торговыми шлюзами, высокоскоростной API для фронтенда). Модульная природа FastAPI идеально ложится на концепцию сквозного примера: мы сможем поэтапно, глава за главой, конструировать архитектуру промышленного уровня без борьбы с монолитными ограничениями фреймворка.
